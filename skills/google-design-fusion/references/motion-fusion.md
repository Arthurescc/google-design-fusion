# Motion Fusion

## Core rule

Motion is a supporting layer, not the visual thesis.

Use `galaxy-motion` to improve:

- hierarchy
- feedback
- waiting states
- state transitions
- CTA response

Do not use it to decorate a weak layout.

## When to introduce motion

Bring motion into the workflow when the request includes:

- CTA or button polish
- loading states
- notifications
- empty states
- hover feedback
- onboarding transitions
- microinteraction finish

If the design problem is still about hierarchy, information architecture, or content clarity, solve that first.

## Good motion roles

- reinforce the primary action
- confirm a successful interaction
- explain a loading or waiting state
- soften a state change
- guide the eye toward a new region

## Bad motion roles

- constant looping animation with no semantic purpose
- motion added just to make the page feel “more premium”
- multiple motion languages stacked in the same region
- hover effects that reduce readability or click confidence

## Recommended fusion order

1. Lock the principle anchor from `design.google`
2. Lock the surface language from `awesome-design-md`
3. Add one or two `galaxy-motion` references for the specific interaction role
4. Write the output with explicit motion placement and guardrails
